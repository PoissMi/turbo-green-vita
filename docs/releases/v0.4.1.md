# Turbo GreenVita 0.4.1

Latency and smoothness. 0.4.0 fixed the upload path; this release fixes the
two problems that were left, and adds the instrumentation that found them.

## The headline: ~1 second of input delay is gone

On 0.4.0 the client could freeze for roughly a second at a time, which read
as an enormous input delay. The cause was in the RTP reassembler, not in the
render path:

The reassembler dropped the in-flight frame the moment a packet with the
next timestamp arrived. On a busy link the tail of a frame routinely arrives
after the head of the next one, so a frame that was merely **late** was
treated as **damaged**. It was thrown away, its late packets were dropped as
stale, and the stream was flagged damaged.

Damaged frames break the H.264 reference chain, so every occurrence
requested a keyframe. A 720p IDR is large and the link is capped at 5 Mbps,
so the keyframe saturated the link, which caused more loss and another
keyframe request — a feedback loop that froze the picture for about a
second at a time.

### What changed

- Incomplete frames are held in a small reorder queue instead of being
  discarded, so a late or retransmitted packet completes the frame and it
  is submitted **in order**.
- The gaps are NACKed as soon as they are detected, not only when the frame
  is given up on, so the retransmission can still arrive in time.
- A frame is abandoned only after a 120 ms repair window (a Wi-Fi round trip
  is 10–40 ms).
- A keyframe is requested only when the damage score trips, not for every
  damaged frame, and the request cooldown dropped from 300 ms to 120 ms.
- The decoder is no longer stopped on damage: it conceals the missing
  reference and keeps producing pictures instead of freezing.

## Every decoded frame now reaches the screen

The display flips at 60 Hz while the source delivers 50–60 frames per second,
so there were already more display slots than source frames — yet only 37
unique frames per second reached the screen. Two frames landing between two
flips meant the older one was superseded and destroyed, at two points in the
path (`repl` at the decode output, `ui-ovr` in the UI slot).

Both handoffs are now bounded queues and the UI takes one frame per display
frame, oldest first. A frame that has waited longer than 50 ms is dropped
rather than shown, so the queue can never make the picture older than it
already was — 50 ms is the worst age the display path already showed.

**On device: unique frames per second 37 → 62, worst-case frame age
unchanged (48.2 → 45.6 ms).**

## Deeper staging ring

Three NV12 staging slots gave a decoded frame only ~50 ms of validity before
the decoder recycled its buffer, and a slow upload meant the frame was
thrown away on the floor. Five slots are now allocated when the memory pool
allows, degrading to three rather than failing to start.

## Audio buffering cut

The sound was queued ~200 ms deep in the SDL device on top of an 80 ms RTP
jitter buffer, so the audio lagged the picture by roughly a third of a second
while the video itself was only ~30 ms old. Perceived latency is anchored on
the sound, so this was the largest latency source left in the client.

- RTP audio jitter buffer: 80 ms → 30 ms
- SDL start buffer: 80 ms → 25 ms
- Device buffer: 1024 → 512 frames (21.3 ms → 10.7 ms)

Total audio buffering: ~180 ms → ~66 ms.

## New HUD fields

The debug HUD now reports the numbers that actually describe latency and
smoothness, rather than proxying them:

| field | meaning |
| --- | --- |
| `age:<avg>/<max>us` | frame age: first RTP packet arrival → upload |
| `in-lag:<avg>/<max>us` | controller sample → handed to the peer connection |
| `pres:<n>` | actual display flips per window (`presented` counts uploads) |
| `gap:<avg>/<max>us` | gap between display flips — the freeze detector |
| `aud:<avg>/<max>ms` | audio queued in the SDL device |
| `ars:<n>` | audio queue overflows (each one is a silent gap) |
| `flush-gap:<max>us` | worst gap between data-channel flushes |
| `kf:<n>` | keyframes requested from the server |
| `handoff:<n>` / `ui-ovr:<n>` | frames handed to the UI / frames dropped before display |

## Included from 0.4.0

- Rotating display textures with per-texture GXM scene tracking
- Overlay throttling with cached replay, and the readable green HUD chip
- TransportLayerNack loss recovery, decode-result queue, 15 ms loop deadline
- Cloud-only UI: no CHOOSE MODE screen
