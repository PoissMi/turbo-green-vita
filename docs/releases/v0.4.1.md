# Turbo GreenVita 0.4.1

Latency and smoothness. 0.4.0 fixed the upload path; this release fixes the
three problems that were left, and adds the instrumentation that found them.

## The headline: ~1 second of input delay is gone

On 0.4.0 the client could freeze for roughly a second at a time, which read
as an enormous input delay. The cause was in the RTP reassembler, not in the
render path:

The reassembler dropped the in-flight frame the moment a packet with the
next timestamp arrived. On a busy link the tail of a frame routinely arrives
after the head of the next one, so a frame that was merely **late** was
treated as **damaged**. It was thrown away, its late packets were dropped as
stale, and the stream was flagged damaged.

Damaged frames break the H.264 reference chain, so every occurrence
requested a keyframe. A 720p IDR is large and the link is capped at 5 Mbps,
so the keyframe saturated the link, which caused more loss and another
keyframe request — a feedback loop that froze the picture for about a
second at a time.

### What changed

- Incomplete frames are held in a small reorder queue instead of being
  discarded, so a late or retransmitted packet completes the frame and it
  is submitted **in order**.
- The gaps are NACKed as soon as they are detected, not only when the frame
  is given up on, so the retransmission can still arrive in time.
- A frame is abandoned only after a 120 ms repair window (a Wi-Fi round trip
  is 10–40 ms).
- A keyframe is requested only when the damage score trips, not for every
  damaged frame, and the request cooldown dropped from 300 ms to 120 ms.
- The decoder is no longer stopped on damage: it conceals the missing
  reference and keeps producing pictures instead of freezing.

## The half-second delay that only appeared after a few minutes

The freeze above was fixed first, but a second delay remained: after a few
minutes of play the character stopped keeping up with the button presses, by
roughly half a second. It read as the whole scene falling behind, and it got
worse the longer the session ran and the higher the bitrate was set.

Every client-side number was clean while it was happening — a 18–27 ms frame
age, 60 display flips per second, a 2 ms input delay to the wire, no loss, no
decoder resets. The client was not the bottleneck, and the new `srv`/`drift`
measurement showed the transport was not either: the video was reaching the
Vita 5 ms after the server's own timestamp, with no growth over a minute.
So the delay had to be in the input path, and the input path had one
difference from both the upstream client and the reference implementation:

    upstream / reference   input channel: reliable, ordered
    this fork (0.4.0)      input channel: unordered, no retransmissions

The backend refactor had silently rewritten the input data channel as an
unordered PR-SCTP stream with zero retransmissions. On such a stream the peer
has to skip the chunks it never received with a forward-TSN, and every chunk
it fails to skip is a gap that the following input waits behind. That is why
the delay grew over the session, and why a busier link made it worse: more
loss, more gaps, more waiting.

The channel is reliable and ordered again, and the controller is now refreshed
every 16 ms instead of 50 ms — the cadence the reference client polls at, so
the server always has a recent state to work with.

The input report's 8-byte uptime stamp was also fixed. The port wrote the age
of the packet, which is always zero because a packet is serialised right after
it is created, so every report carried the same stamp. The reference client
fills it with its uptime (`performance.now()`), and a stream of reports whose
stamp never moves looks like a frozen client.

**On device: the delayed reaction is gone.**

## Every decoded frame now reaches the screen

The display flips at 60 Hz while the source delivers 50–60 frames per second,
so there were already more display slots than source frames — yet only 37
unique frames per second reached the screen. Two frames landing between two
flips meant the older one was superseded and destroyed, at two points in the
path (`repl` at the decode output, `ui-ovr` in the UI slot).

Both handoffs are now bounded queues and the UI takes one frame per display
frame, oldest first. A frame that has waited longer than 50 ms is dropped
rather than shown, so the queue can never make the picture older than it
already was — 50 ms is the worst age the display path already showed.

**On device: unique frames per second 37 → 62, worst-case frame age
unchanged (48.2 → 45.6 ms).**

## Deeper staging ring

Three NV12 staging slots gave a decoded frame only ~50 ms of validity before
the decoder recycled its buffer, and a slow upload meant the frame was
thrown away on the floor. Five slots are now allocated when the memory pool
allows, degrading to three rather than failing to start.

## Audio buffering cut

The sound was queued ~200 ms deep in the SDL device on top of an 80 ms RTP
jitter buffer, so the audio lagged the picture by roughly a third of a second
while the video itself was only ~30 ms old. Perceived latency is anchored on
the sound, so this was the largest latency source left in the client.

- RTP audio jitter buffer: 80 ms → 30 ms
- SDL start buffer: 80 ms → 25 ms
- Device buffer: 1024 → 512 frames (21.3 ms → 10.7 ms)
- The queued audio is now capped at 120 ms; when the queue would overflow it
  is dropped and refilled instead of growing without bound (each overflow used
  to leave a short silent gap, counted as `ars`).

Total audio buffering: ~180 ms → ~66 ms.

**On device: audio queued in the device 212 ms → 39 ms, no overflows.**

## The server's video delay is now measured, and the bitrate estimate follows it

The frame age the HUD reports starts when a packet leaves the socket buffer,
so a queue that grows in front of the client is invisible to it: every frame
looks fresh while the picture itself falls further and further behind reality.
The RTP timestamp is the server's capture time, so the gap between it and our
arrival clock is exactly that hidden delay. It is now measured and reported as
`srv` (how far the server's timeline lags our clock) and `drift` (how much
that grew over the last minute), together with `rx-b`, the number of packets
drained per socket read.

The server sizes its encoder from the REMB we send, and it asks for it once a
second. The estimate now follows the measurement: it backs off while the
queue is growing and climbs back towards the setting in Settings when the path
keeps up. The setting stays the ceiling — the estimate only drops when the
path cannot sustain it.

## New HUD fields

The debug HUD now reports the numbers that actually describe latency and
smoothness, rather than proxying them:

| field | meaning |
| --- | --- |
| `age:<avg>/<max>us` | frame age: first RTP packet arrival → upload |
| `in-lag:<avg>/<max>us` | controller sample → handed to the peer connection |
| `in-wire:<avg>/<max>us` | input report queued → out on the wire |
| `in-rate:<n>` | input reports sent per second |
| `pres:<n>` | actual display flips per window (`presented` counts uploads) |
| `gap:<avg>/<max>us` | gap between display flips — the freeze detector |
| `aud:<avg>/<max>ms` | audio queued in the SDL device |
| `ars:<n>` | audio queue overflows (each one is a silent gap) |
| `flush-gap:<max>us` | worst gap between data-channel flushes |
| `kf:<n>` | keyframes requested from the server |
| `handoff:<n>` / `ui-ovr:<n>` | frames handed to the UI / frames dropped before display |
| `srv:<ms>` | how far the server's video timeline lags our clock |
| `drift:<ms>` | how much that grew over the last minute |
| `remb:<kbps>` | bitrate currently requested from the server |
| `rx-b:<avg>/<max>` | packets drained per socket read |
